# Connected cook recording

Debug and Firebase Dev builds can attach a GrillirG, provisioned Pit Boss/Louisiana Dansons controller, or Traeger WiFIRE grill to a local cook. The new providers are experimental with hardware confirmation pending. Each provider has its own explicit setup and encrypted session. PitTech exposes only authentication/discovery/telemetry operations; there are no grill-control requests. See [provider compatibility and research](GRILL_PROVIDER_RESEARCH.md).

## User flow

1. Connect/select a grill in Devices. Start a cook, select **Save grill temperatures with this cook**, choose a collection interval (one minute by default) or **When I log something**, and optionally assign the available Probe 1–4 channels to dishes. Existing active cooks can use **Attach grill & record** in Live.
2. Live shows chamber, reported setpoint, food channels, receipt age, connection state, and recent history. **Assign probes to dishes** preserves each prior assignment interval and each reading's original dish.
3. Food on, spritz, wrap, remove and rest quick actions create ordinary editable cook entries. Notes, reminder check-ins and events copy available preceding temperature values. A copied snapshot cannot change when a source reading is edited/deleted.
4. New camera photos preserve the temporary camera file's capture time. Library EXIF dates are accepted only with an explicit offset; ambiguous dates stay unknown. Photos obtain their own context at capture time, not import time. A default photo timeline entry follows known capture time; an unknown gallery date clears its automatic context. Explicitly backdated entries retain their chosen time. Entries/photos without relevant recent data have no fabricated context.
5. Pause/stop recording independently of the cook. Pausing a cook pauses recording. Resume recording is explicit. Finishing/deleting serializes with ingestion and prevents late samples being added. Restore imports history in a stopped state and never starts background recording.

One selected grill can record into one active cook at a time, with multiple dishes/probes in that cook. A running recording locks both provider and grill selection. After pausing, selecting another provider or grill requires an explicit attachment in the cook. Earlier samples retain their original local device and dish attribution. A restored cook can attach a grill again; cloud identities and authentication credentials are never exported.

## Collection and timestamps

The shared cloud monitor has one serial poller, with 15-second, 30-second, one-minute, two-minute and five-minute presets. Timed recording has a separate service owner so activity/camera changes do not cancel it. A persistent notification offers Pause, and a continuously renewed CPU wake lease supports the requested screen-off cadence. Slower polling reduces collection cycles, not necessarily CPU or total battery cost. Setup and Live expose Android battery-exemption, notification/channel and Battery Saver controls, with status refreshed after returning from Settings. Android/vendor restrictions, network loss and stopping the app can still interrupt recording; missed data cannot be backfilled.

**When I log something** requests bounded snapshots for new log/photo/check-in actions and closes live connections afterward, with no idle poll/retry timer, recording service or wake lease. An observation no more than 15 seconds old may be reused for rapid entries. A failed query never prevents saving the log. Camera snapshots are requested before camera launch; historic/unknown capture times never get temperatures from a later query. Sparse readings remain separate graph points. See [power analysis, Android API choices and validation](RECORDING_POWER_AND_SAMPLING.md).

Encrypted authentication can recover an active session on reopening. Traeger renews a saved refresh token when needed. Expired/displaced or unsupported authentication requires explicit reconnection/resume. Production service/power-policy review and a physical overnight test remain necessary.

The debug/Dev service declares `specialUse` with its continuous, user-visible cook-monitoring rationale. It is absent from the regular release manifest. This does not claim Google Play approval: this declaration must be reviewed before promoting the integration to the production app. `dataSync` is inappropriate for assuming an unattended cook longer than its Android 15+ six-hour allowance; periodic WorkManager is not a 15-second sampler. See [service types](https://developer.android.com/develop/background-work/services/fgs/service-types) and [timeouts](https://developer.android.com/develop/background-work/services/fgs/timeout).

Automatic readings explicitly carry `timestampBasis=cloud_receipt`: receipt time is known. When a provider supplies a device report timestamp, PitTech also rejects stale or repeated reports without relabeling that device timestamp as receipt time. A recent HTTP response does not prove fresh sensor data. Vendor-reported offline readings are not inserted as valid temperatures. Missing probe/setpoint values are unavailable channel samples. GrillirG's confirmed unplugged zero probes stay unavailable; its probe status is alarm arming, not plug detection. Dansons preserves 960 sentinels, and Traeger uses connected flags and stable accessory channels. A connected probe reading 0°C is valid for these providers. Missing unit means no temperatures can be normalized. Graphs split at unavailable samples, receipt gaps longer than the selected interval plus 30 seconds (at least 45 seconds), on-log snapshots, and probe reassignment; no interpolation or history backfill is invented. Display reduction preserves segment endpoints/extremes while the database/export keeps every sample.

Room transactions enforce cook status, binding, resume watermark and per-sample IDs during ingestion. Repeated monitor emissions cannot duplicate samples. Connection interruptions/restoration are bounded timeline events; a reported setpoint change needs two consecutive agreeing observations. Operating codes do not start/finish cooks automatically.

## Local data and archive compatibility

Room schema 5 adds per-cook mode/interval and per-reading cadence to the recording state, probe assignments, context and timestamp basis introduced in schema 4. Migrations 3→4→5 preserve older data and its legacy 15-second collection policy. Archive schema 4 exports mode/interval in JSON, CSV and workbook; schemas 1–3 remain importable with legacy defaults. Exports contain only local device/probe IDs. Controller binding hashes are omitted and imports force recording status to stopped.

## Verification

The JVM suite checks temperature normalization, unavailable channels, timestamp-based context, copied snapshots, graph gaps/reassignment, display reduction, recording ownership and selection locking. Android integration tests cover binding/duplicate/finish guards, immutable snapshots and camera timestamps, assignment history, gap/setpoint events, archive restore, schema migration, foreground recording across activity backgrounding and terminal authentication failure, plus starting a recorded cook and saving a wrap through the UI. The existing data-preserving APK upgrade and app flows remain in the CI gate. Synthetic backend tests validate app behavior; a physical overnight/network-interruption test is still required to measure this controller/cloud/phone combination in practice.
