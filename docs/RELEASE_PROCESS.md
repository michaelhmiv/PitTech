# Releases, changelogs and store update notes

PitTech has three different audiences: developers reading GitHub history, testers on Firebase/Play closed testing, and users reading app-store update descriptions. Each needs accurate notes tied to code that actually shipped.

## Sources of truth

- [CHANGELOG.md](../CHANGELOG.md) tracks notable changes and dates. Historical baseline entries are not invented releases.
- [.github/release.yml](../.github/release.yml) categorizes PRs when GitHub generates release notes for a tagged release. Review autogenerated text before publication; PR titles can be internal or misleading.
- [Google Play English (US) What's New](../distribution/play/whatsnew/whatsnew-en-US) is the manually reviewed user-facing Play description, with a 500-character limit.
- [App Store What's New](../distribution/app-store/whats-new-en-US.txt) is the manually reviewed iOS description for later versions; iOS differs substantially from Android.
- Firebase Dev notes are generated from the commit entering main and linked to the exact commit. They are tester-facing diagnostics, not a substitute for reviewed public changelogs.

## Required release procedure

1. Review merged PRs since the last *actual* release and update `CHANGELOG.md`. Verify every claim against the target platform and tested commit; do not claim a planned Beta connection is shipped.
2. Rewrite the appropriate store description in plain language. `python3 scripts/release_notes.py validate` checks required files, lengths, and placeholders, but cannot validate factual truth.
3. For Android, run the maintained Play release workflow; it tests and builds from `main` and passes `distribution/play/whatsnew/` to the publisher. Production still requires the existing manual readiness confirmation and a staged rollout.
4. For iOS, attach the reviewed iOS notes in App Store Connect during manual upload. The current iOS workflow builds an IPA but does not upload or submit it.
5. For a public version, create a real Git tag for the verified commit (for example `v0.1.0`) and generate a **draft** GitHub Release from that tag. Review PR categories, exact platform coverage, and any known limitations, then publish the release.
6. Link the release to the version and tested commit in the changelog. Keep Firebase-only builds out of public Releases unless deliberately offering them.

## Notes checklist

- Lead with changes that users can see.
- Mention meaningful data migration, compatibility or privacy changes.
- Do not advertise read-only device integrations until the release artifact actually includes an authorized, tested connector.
- Keep “Beta” in public connection labels and describe gaps, outages and other limitations.
- Review release notes for secrets, internal architecture details and vendor/private endpoint identifiers.
- Do not automatically publish release notes based only on commit messages; automatic GitHub notes are drafts.

## Repository presentation

Recommended GitHub About description:

> Open-source BBQ cooking companion for logging cooks, tracking temperatures, saving recipes, and learning from every smoke.

Suggested topics: `bbq`, `smoking`, `cooking`, `android`, `kotlin`, `jetpack-compose`, `open-source`, `food`.

The repository About description, topics and homepage require repository administration permissions. Update them in the GitHub repository's **About** settings when those permissions are available. Use only a working public homepage or support URL. The README itself is version-controlled by this project.

## Production gates

Run Android JVM tests and the required API 36 emulator lanes on the exact release commit before publishing; record their workflow run. Validate permissions and vendor authorizations separately from code checks. The Play workflow should not be mistaken for a replacement for the full emulator matrix.

A GitHub PR merge is not a release and should not automatically promote changes to Google Play production or the Apple App Store.
